# Onboard (adopt an existing repo)

This skill is where `new-project` routes when the repo already exists. Its
job is not to redesign the project — it is to find out, cheaply and
truthfully, what is already there, write that down as `docs/SITUATION.md`,
and then propose which acdev artifacts are worth adding on top of it.

## Read before writing

Inventory the repo before writing anything. Every fact goes into the
situation map with a tag naming its source class, in this order of
precedence, highest first:

1. **`[user]`** — explicit statements the user makes this session. These
   override anything found in the repo; if the user says the deploy target
   is X, that wins even if the code suggests otherwise (record the
   conflict instead of silently picking one).
2. **`[docs]`** — existing documentation: README, VISION, ADRs, wikis. Docs
   from a proyecto-kike-era project are compatible with acdev and count as
   `[docs]` evidence, not as noise to discard.
3. **`[code]`** — code and config reality: package manifests, migrations,
   CI workflow files, deploy configs, environment files. This is read when
   docs are silent or contradict what the code actually does.
4. **`[git]`** — git history: recent commit activity, cadence, contributor
   count. Weakest evidence class; use it for freshness and activity signals,
   not for product intent.

Anything not found after checking the sources above is a **declared gap**
— written as a gap line (for example "no deploy configuration found
`[gap]`"), never filled in with a guess. A gap is a legitimate, complete
answer; an invented fact is not.

Use subagents for wide scans (searching the tree for config files, reading
CI workflows, scanning for auth/data-layer code across many files). Read
their conclusions back into the map, not raw file dumps — this keeps the
onboarding pass cheap regardless of repo size.

## Situation map

Write `docs/SITUATION.md` using `references/situation-map.md`. It covers:

- **Product (observed)** — what the product does and who it is for, as
  observed, not as aspired.
- **Stack (observed)** — languages, frameworks, data store, hosting,
  observed from manifests and config, not assumed from the domain.
- **Layer state** — one row per acdev layer (frontend, api, data, auth,
  security, performance, delivery, cicd), each marked present / partial /
  absent / unknown, with one evidence line per row.
- **Documentation state** — what already exists and how current it is
  against the code.
- **Tests and CI** — what runs today, and what does not.
- **Declared gaps** — everything looked for and not found.
- **Risks** — what the gaps and partial states above put at risk.

Every factual line in the document ends with its source tag. A line
without one does not belong in the map.

## Confirm and adopt

Present the situation map to the user. They correct it — wrong reads,
missing context only they have, outdated assumptions baked into old code.
Update the map with their corrections, tagged `[user]`.

**GATE.** Ask for explicit confirmation that the map is accurate before
proposing anything. Do not propose the adoption plan until the map itself
is confirmed — a plan built on an unconfirmed map inherits its errors.

Once confirmed, propose the adoption plan:

- **VISION.md retroactively, if absent.** Written the same way as in
  `new-project` stage 1 — conversed with the user section by section using
  `shared/references/templates/vision.md`, never autogenerated from the
  situation map alone. The map informs the conversation; it does not
  replace it.
- **MVP.md, only if unbuilt scope remains worth gating.** If the product is
  already complete against its own ambitions, skip it and say why. If
  meaningful scope is still unbuilt, cut it the same way `new-project`
  stage 2 does.
- **Blueprint deltas.** Decisions already embodied in the code but never
  recorded (stack, hosting, data store, auth approach, tenancy model) get
  written as ADRs marked "as-built" in their Context section, using
  `shared/references/templates/adr.md` — this closes the paper-trail gap
  without pretending the decision is being made now.
- **Initial pipeline state.** Write `.acdev/state.md` and the first
  checkpoint by running:

  ```
  node "${CLAUDE_PLUGIN_ROOT}/scripts/checkpoint.mjs" write --stage <s> --branch <b> --next "<text>"
  ```

  `--stage`, `--branch`, and `--next` are required. Set `--stage` to the
  pipeline stage the project should resume at (per the adoption plan just
  agreed), and `--next` to the concrete next action.

Hand off to whichever skill matches that resume stage — `blueprint` if
VISION/MVP already exist or were just written and only the normative
package is missing, `mockups` if screens are still needed, `build` if the
project is fully documented and mid-construction.

## Rules

- Never rewrite an existing doc without showing the diff and getting
  confirmation first. Adoption augments what exists; it does not silently
  overwrite it.
- Where an existing convention conflicts with an acdev default (naming,
  doc structure, ADR format), the existing convention wins — record the
  conflict in the situation map rather than resolving it unilaterally.
- Commit: `docs: acdev onboarding and situation map`.
