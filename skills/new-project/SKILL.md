# New project (stages 0-2)

This skill runs the first three stages of the acdev pipeline: intake, VISION.md, and MVP.md. It is the entry point for any brand-new project. Two hard approval gates lie ahead: VISION.md and MVP.md must each be explicitly approved by the user before the pipeline moves on. After MVP.md is approved, the pipeline continues into the `mockups` skill (or skips to `blueprint` when the project has no UI).

## Stage 0 - Intake

Open with ONE question and nothing else: ask the user to tell, in a few
sentences, what they want to build and for whom. Listen before any form —
the idea comes first, the paperwork second. Then ask the remaining intake
questions in one message (`references/intake.md`), proposing defaults
derived from what was just told.

An existing repo not yet on acdev stops this skill: the user runs
`/acdev:onboard` instead — do not run the VISION/MVP interview on an
existing codebase. A repo that already runs the pipeline (`.acdev/`
exists) stops too: changes to an adopted product are VISION/MVP amendments
made through the pipeline, not a new project.

With the answers in hand, and before any document is written, install the
guard per `shared/references/guard-install.md` and write the initial
pipeline state (`--stage vision`, `--lang` set to the documentation
language; commands in `references/intake.md`). From this point the "zero
product code" rule is enforced by a hook that reads that state, not by
memory: it denies writes outside docs until the build stage, and asks
before an approved document is edited again. Paste the `status` output as
evidence the guard is live.

## Stage 1 - VISION.md (HARD GATE)

VISION.md is the source of truth: every later document, and eventually all code, derives from it. It is never autogenerated — it is conversed, and the user watches it grow: every answer lands as document text they see and correct on the spot, so the final gate approves a document they have already read.

Run the interview per the Procedure in `references/vision-questionnaire.md`:
scaffold `docs/VISION.md` in the language chosen at intake, then its 7
sections one at a time, each drafted first, challenged when weak, shown as
it will read in the document and Edited into the file before moving on.
Once all 7 sections are agreed the document is complete: there is no
separate whole-document write.

**HARD GATE.** Present the full document — never a summary: the user approves what they read, and by now none of it should be new — and ask, in these words or equivalent: "Do you approve this VISION document?" Do not create MVP.md, mockups, or any other artifact until the answer is an explicit approval. A partial or implied approval does not count — this document is the foundation everything else derives from. If the user asks for changes, Edit the changed section, show that section, then present the full document once more and ask for approval of the full document again. Repeat until approved.

On approval, advance the state (`--stage mvp`) and commit: `docs: project
vision`. The guard now asks before `docs/VISION.md` is edited again.

## Stage 2 - MVP.md (HARD GATE)

MVP.md is the first-delivery contract, cut from the approved VISION — it is not a new invention, it is a derivation.

Cut it per `references/mvp-guide.md`: scaffold `docs/MVP.md` in the intake
language, then the IN list (numbered, each item traceable to a flow in
VISION §5), the OUT list (as explicit and complete as IN, each item naming
the phase it moves to from VISION §7) and success criteria as verifiable
facts, not wishes; each section previewed, corrected and Edited into the
file the same way as stage 1, with no whole-document write.

**Derivation rule.** If cutting the MVP reveals a gap, contradiction, or missing decision in VISION, STOP. Fix VISION.md first, with the user, and only then continue cutting the MVP. Never patch the gap directly into MVP.md — a child document does not get to disagree with its source.

**HARD GATE.** Ask for explicit approval of the full MVP.md document, the same way as stage 1. Iterate until approved. Then advance the state (`--stage mockups`, or `--stage blueprint` when the skip-by-scope below applies) and commit: `docs: mvp contract`.

## Rules

- Zero product code in stages 0-2. No implementation, no scaffolding, no "just a quick prototype."
- No placeholders anywhere in generated documents. A missing fact is either asked of the user or explicitly declared as an open question — never invented, never left as `TBD` silently.
- All generated artifacts (VISION.md, MVP.md) are written in the documentation language chosen at intake, which is not necessarily English.
- Next step after MVP.md is approved: if the MVP has UI (per VISION §5/§6), continue with the `mockups` skill. If it has no UI (CLI, pure API, worker), propose skipping directly to the `blueprint` skill (skip-by-scope) and get the user's confirmation before skipping.
