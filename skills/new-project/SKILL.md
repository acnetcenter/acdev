# New project (PRODUCT.md and MVP.md)

Two documents, two gates. `docs/PRODUCT.md` is the source of truth every
later document and all code derive from; `docs/MVP.md` is the first
delivery, cut from it. Both record the user's decisions, so they are
conversed, never autogenerated, and each needs an explicit approval before
anything else is produced. After the MVP gate the pipeline continues with
`mockups`, or with `blueprint` when the product has no UI.

## Intake

Open with one question and nothing else: what do they want to build, and
for whom. Listen first; then ask the remaining intake questions in one
message (`references/intake.md`), proposing defaults from what was told.

Two situations stop this skill. A repo that already has code but no
`.acdev/` is adopted with `/acdev:onboard`, which the user runs. A repo
that already has `.acdev/` runs the pipeline: a change to its product is
an amendment to PRODUCT.md or MVP.md, not a new project.

`acdev` is the plugin's CLI in the Bash tool; in PowerShell call it as
`node "${CLAUDE_PLUGIN_ROOT}/scripts/acdev.mjs"`.

Before any document is written, run `acdev init` and write the first
state (`acdev checkpoint write --stage product ...`; both commands are in
`references/intake.md`). From then on the guard denies product code until
the build stage; paste `acdev status` as evidence that it is live.

## Size the interview to the project

A personal tool or an internal utility gets the short path: draft the
whole PRODUCT.md from the idea in one reply and correct it with the user
in a round or two. A product for sale, or anything multi-tenant, with
payments or with personal data, goes section by section. Say which path
you are taking and why; the user can switch. The gate is the same.

## PRODUCT.md (gate)

Follow `references/product-questionnaire.md`: scaffold `docs/PRODUCT.md`
in the documentation language, draft each answer from what the user
already said, challenge the weak ones, and Edit the agreed text into the
file as you go. If `docs/PRODUCT.md` already exists (a design tool may
have written it), read it first, keep what is confirmed and add what is
missing; never overwrite it.

The user approves what they read. A tool call is not a preview: they do
not read Edit diffs or `cat` output, so a section is pasted in the reply
before any question about it.

**Gate.** Paste the full document in the reply, never a summary, and ask:
"Do you approve this PRODUCT document?" Create nothing else until the
answer is an explicit approval; a partial or implied yes does not count,
because everything downstream derives from this document. For a change,
Edit the section, show it, then present the full document again.

On approval advance the state (`--stage mvp`) and commit `docs: product`.
The guard now stops any edit of `docs/PRODUCT.md` until the user agrees.

## MVP.md (gate)

Cut the first delivery per `references/mvp-guide.md`: the IN list (each
item traceable to a critical flow in PRODUCT.md), the OUT list (as
explicit as IN, grouped by the later phase each item moves to) and
success criteria as verifiable facts.

If the cut reveals a gap or a contradiction in PRODUCT.md, stop and fix
PRODUCT.md first, with the user. A child document does not get to
disagree with its source.

**Gate.** Ask for explicit approval of the full MVP.md document, pasted in
the reply, the same way. On approval advance the state (`--stage mockups`,
or `--stage blueprint` when the product has no UI and the user confirms
the skip) and commit `docs: mvp contract`.

## Rules

- Zero product code here: no implementation, no scaffolding, no quick
  prototype. The guard enforces it; a denial is a gate, not an obstacle.
- No placeholders anywhere in generated documents. A missing fact is
  asked of the user or written down as an open question with an owner.
- Both documents are written in the documentation language chosen at
  intake.
