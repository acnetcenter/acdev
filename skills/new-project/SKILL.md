# New project (stages 0-2)

This skill runs the first three stages of the acdev pipeline: intake, VISION.md, and MVP.md. It is the entry point for any brand-new project. Two hard approval gates lie ahead: VISION.md and MVP.md must each be explicitly approved by the user before the pipeline moves on. After MVP.md is approved, the pipeline continues into the `mockups` skill (or skips to `blueprint` when the project has no UI).

## Stage 0 - Intake

Open with ONE question and nothing else: ask the user to tell, in a few
sentences, what they want to build and for whom. Listen before any form —
the idea comes first, the paperwork second.

Then, with the idea on the table, ask the remaining intake questions in one
message, proposing defaults derived from what was just told:

1. Project name (propose one from the idea).
2. New repository or existing one? If existing and not yet on acdev, stop this skill and have the user run `/acdev:onboard` instead — do not run the VISION/MVP interview on an existing codebase. If it already runs the pipeline (`.acdev/` exists), stop too: changes to an adopted product are VISION/MVP amendments made through the pipeline, not a new project.
3. Documentation language: the language every generated artifact (VISION.md, MVP.md, and everything downstream) will be written in.
4. Claude Code only, or multi-AI (Codex, Cursor, Copilot, ...)? This decides whether an `AGENTS.md` mirror of `CLAUDE.md` is generated later, at blueprint stage.

With the answers in hand, and before any document is written, install the
guard per `shared/references/guard-install.md` and write the initial
pipeline state (`--stage vision`, `--lang` set to the documentation
language). From this point the "zero product code" rule is enforced by a
hook that reads that state, not by memory: it denies writes outside docs
until the build stage, and asks before an approved document is edited
again. Paste the `status` output as evidence the guard is live.

## Stage 1 - VISION.md (HARD GATE)

VISION.md is the source of truth: every later document, and eventually all code, derives from it. It is never autogenerated — it is conversed, and the user watches it grow: every answer lands as document text they see and correct on the spot, so the final gate approves a document they have already read.

1. Open `references/vision-questionnaire.md` and work through its 7 sections one at a time (blocks of 2-3 only if the user asks for speed).
2. For each section, propose a draft answer first, seeded from everything already told — the intake idea covers much of the early sections; the user corrects a draft faster than they compose one from a blank page.
3. Challenge weak answers. "For everyone" is not a target market — ask who is NOT a customer. "As complete as possible" is not a scope — ask what is explicitly out of the v1.
4. Close each section by showing it as it will read in the document — "this is what we have so far" — and let the user correct or extend it right there before moving on. These running previews ARE the document being written; by the last section the user has seen every line of it.
5. Once all 7 sections are agreed, write `docs/VISION.md` using `shared/references/templates/vision.md`, in the language chosen at intake.
6. **HARD GATE.** Present the full document — never a summary: the user approves what they read, and by now none of it should be new — and ask, in these words or equivalent: "Do you approve this VISION document?" Do not create MVP.md, mockups, or any other artifact until the answer is an explicit approval. A partial or implied approval does not count — this document is the foundation everything else derives from.
7. If the user asks for changes, revise and ask for approval of the full document again. Repeat until approved.
8. Advance the state (`node "<plugin-root>/scripts/checkpoint.mjs" write --stage mvp --branch <branch> --next "cut MVP.md from the approved VISION"`) and commit: `docs: project vision`. The guard now asks before `docs/VISION.md` is edited again.

## Stage 2 - MVP.md (HARD GATE)

MVP.md is the first-delivery contract, cut from the approved VISION — it is not a new invention, it is a derivation.

1. Open `references/mvp-guide.md` and use it to cut the MVP from the approved VISION.md.
2. Define what is IN: a numbered feature list, each item traceable to a flow in VISION §5.
3. Define what is explicitly OUT: as explicit and complete as the IN list, each item naming the phase it moves to (from VISION §7's phase sketch).
4. Define success criteria as verifiable facts, not wishes ("10 real users complete flow X unaided", not "users like it").
5. Write `docs/MVP.md` using `shared/references/templates/mvp.md`, in the intake language.
6. **Derivation rule.** If cutting the MVP reveals a gap, contradiction, or missing decision in VISION, STOP. Fix VISION.md first, with the user, and only then continue cutting the MVP. Never patch the gap directly into MVP.md — a child document does not get to disagree with its source.
7. **HARD GATE.** Ask for explicit approval of the full MVP.md document, the same way as stage 1. Iterate until approved.
8. Advance the state to the next stage (`--stage mockups`, or `--stage blueprint` when the skip-by-scope below applies) and commit: `docs: mvp contract`.

## Rules

- Zero product code in stages 0-2. No implementation, no scaffolding, no "just a quick prototype."
- No placeholders anywhere in generated documents. A missing fact is either asked of the user or explicitly declared as an open question — never invented, never left as `TBD` silently.
- All generated artifacts (VISION.md, MVP.md) are written in the documentation language chosen at intake, which is not necessarily English.
- Next step after MVP.md is approved: if the MVP has UI (per VISION §5/§6), continue with the `mockups` skill. If it has no UI (CLI, pure API, worker), propose skipping directly to the `blueprint` skill (skip-by-scope) and get the user's confirmation before skipping.
